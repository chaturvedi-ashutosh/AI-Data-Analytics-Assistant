# Asklytics — AI Data Analytics Assistant

Asklytics is a local, read-only analytics workspace. Ask a business question in plain language, inspect the SQL generated by a local Ollama model, and explore the result as a chart, KPI, or table. The application includes query history, a schema explorer, saved dashboard results, and appearance settings.

## Features

- Natural-language SQL generation using a local Ollama model.
- Schema-aware SQL validation, one repair attempt for invalid generated SQL, and clarification responses for ambiguous questions.
- PostgreSQL execution through a restricted read-only role, with a five-second analytics query timeout and a 500-row result cap by default.
- Result insights and automatic chart selection (line, bar, donut, KPI, or table).
- Conversational follow-ups. The backend keeps the previous question and validated SQL in process memory for up to 30 minutes; restarting the backend clears it.
- Workspace, query history, schema explorer, pinned-result dashboards, and settings for theme, accent, density, and default chart type.
- Browser-local storage for history (up to 100 questions), saved results (up to 20), and preferences. This data is not synchronized between browsers.

## Requirements

- Node.js 20 or newer and npm
- PostgreSQL 14 or newer, with `psql` available (or pgAdmin for database setup)
- Ollama installed locally and the configured model downloaded

## Install

From the project root:

```sh
npm install
```

## Set up PostgreSQL

Create the sample database and tables using an administrative account. These commands are for PowerShell and may prompt for the PostgreSQL password:

```powershell
psql -h localhost -U postgres -d postgres -f backend/db/sql/00_create_database.sql
psql -h localhost -U postgres -d analytics_db -f backend/db/sql/01_schema.sql
psql -h localhost -U postgres -d analytics_db -f backend/db/sql/02_seed.sql
psql -h localhost -U postgres -d analytics_db -f backend/db/sql/03_readonly_role.sql
```

The seed data is repeatable and includes regions, customers, products, orders, and order items with dates across 2024–2026. The role script creates/configures `analytics_user` with limited read access, excludes customer names and email addresses, and enforces read-only transactions. Run setup scripts as the database owner or administrator. The application itself must connect as `analytics_user`.

If using pgAdmin, select `analytics_db`, open **Tools → Query Tool**, and execute `01_schema.sql`, then `02_seed.sql`. Execute `03_readonly_role.sql` as the database owner/admin. Run `00_create_database.sql` against the `postgres` database if `analytics_db` does not yet exist.

## Configure and start

Copy the backend template and edit `backend/.env` with the password set for `analytics_user`:

```powershell
Copy-Item backend/.env.example backend/.env
```

At minimum, set `DATABASE_URL`, for example:

```text
DATABASE_URL=postgresql://analytics_user:your_password@localhost:5432/analytics_db
```

The backend also supports individual `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, and `DB_PASSWORD` settings. `backend/.env.example` documents the API, database pool, query limit, and Ollama settings. The defaults use Ollama at `http://127.0.0.1:11434` with `qwen2.5-coder:7b`; pull the model if needed:

```sh
ollama pull qwen2.5-coder:7b
```

Start Ollama, then run each app in a separate terminal from the project root:

```sh
npm run dev:backend
```

```sh
npm run dev:frontend
```

Open <http://localhost:5173>. In local development, Vite proxies `/api` requests to Express at `http://localhost:3000`. Set `VITE_API_BASE_URL` in `frontend/.env` only when using a different API URL; otherwise leave it empty. Do not commit `backend/.env`.

For a production frontend build, run `npm run build` from the root. The backend has `npm --prefix backend start` for starting the API without watch mode.

## Application pages

- **Workspace (`/`)** — Ask questions, continue follow-ups, inspect generated SQL, browse charts/tables/insights, and pin successful results. `Ctrl/Cmd + K` starts a new chat; `/` focuses the question composer; `Esc` cancels the current browser request.
- **History (`/history`)** — Search, pin, and rerun questions saved in this browser.
- **Schema (`/schema`)** — Browse exposed tables, columns, keys, and foreign-key relationships; select a name to insert it into a Workspace question.
- **Dashboards (`/dashboards`)** — Review and remove pinned result snapshots saved in this browser.
- **Settings (`/settings`)** — Choose light/dark/system theme, accent, density, and default chart type.

## API

| Method and path | Purpose |
| --- | --- |
| `GET /api` | API name and status |
| `GET /api/health` | API and PostgreSQL health (`503` if the database is unavailable) |
| `GET /api/schema` | Accessible tables, columns, types, nullability, defaults, primary-key flags, and foreign keys in `public` |
| `POST /api/analyze` | Generate, validate, execute, and analyze a question |

Example request:

```json
{
  "question": "Show monthly revenue",
  "conversationId": "f83a16cb-3925-40d9-97f6-0ace935e3fb9"
}
```

`question` is required (3–1000 characters); `conversationId` is an optional UUID used for follow-up context. Successful responses contain the question, validated SQL, explanation, columns and metadata, rows, insight, visualization, truncation flag, execution time, and `status: "success"`. Ambiguous questions return `status: "clarification_needed"` and an explanation without executing SQL. Unsafe or invalid generated SQL returns HTTP 422 with `status: "rejected"`.

## SQL safety

Generated SQL is treated as untrusted input. The validator allows a single read-only query and checks table/column access, functions, CTEs, and foreign-key joins. Invalid SQL can be regenerated once with validation feedback. Accepted queries execute in a read-only transaction using the configured analytics role, statement timeout, and row cap. PostgreSQL permissions provide an additional boundary; the model does not connect to the database or execute queries itself.
